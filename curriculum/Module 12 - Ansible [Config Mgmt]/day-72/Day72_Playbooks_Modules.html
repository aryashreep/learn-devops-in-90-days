Ansible Playbooks & Modules

Day 72: Write once, automate everywhere! 📝

Golu
"Jagu! I wrote a bash script to configure my servers, but when I run it again it breaks everything! And the syntax is so messy..."
"Beep Boop! That's because bash scripts are NOT idempotent. Ansible playbooks are! You declare the desired state and Ansible figures out what to change. Run it 100 times — same result!"
Jagu
🎯 Learning Objectives
  • Write YAML playbooks with plays, tasks, and variables.
  • Use core modules: apt, yum, copy, file, service, debug.
  • Understand idempotency — running the same playbook multiple times yields the same result.
  • Run playbooks with check mode, verbose output, and syntax validation.
📝 Playbook Structure
---
- name: Web Server Setup
  hosts: webservers
  become: yes
  vars:
    app_port: 8080

  tasks:
    - name: Install Nginx
      ansible.builtin.apt:
        name: nginx
        state: present

    - name: Create web directory
      ansible.builtin.file:
        path: /var/www/html
        state: directory
        mode: '0755'

    - name: Deploy index page
      ansible.builtin.copy:
        src: index.html
        dest: /var/www/html/index.html

    - name: Start Nginx
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: yes
🔧 Core Modules
ModulePurposeExample

▶ Running Playbooks
# Basic run
ansible-playbook site.yml

# Check mode (dry run) — see changes without applying
ansible-playbook -C site.yml

# Check mode with diff (see exact file changes)
ansible-playbook -C --diff site.yml

# Verbose logging
ansible-playbook -vvv site.yml

# Syntax check only
ansible-playbook --syntax-check site.yml

Jagu's Rule: Always run --check --diff before applying to production!
