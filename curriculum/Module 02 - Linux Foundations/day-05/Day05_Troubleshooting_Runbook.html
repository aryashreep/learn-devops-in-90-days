What will we learn today?

Today we will look for Linux troubleshooting. How to take snapshot of CPU, RAM, Disk and Logs and write a repeatable 'Runbook'.

🎯 LEARNING OBJECTIVES
  • Monitor: CPU and RAM health using `top` and `htop`.
  • Analyze: Disk space and I/O with `df` and `du`.
  • Trace: Deep-dive into system logs in `/var/log`.
  • Repeat: Learn what a 'Runbook' is and how to create one.

📂 The SRE's Radar — Where to Monitor
  • 🔍 /var/log/syslog → Overall system health and errors.
  • 🌐 /var/log/nginx/ → Web server specific access and error logs.
  • ⚙️ /proc → Virtual filesystem for real-time kernel info.
📌 Key Concepts: Vitals Check

CPU / RAM

top / free -h

Disk Space

df -h / du -sh

Logs

tail -n 50 / journalctl

Strategy: Capture evidence BEFORE taking action!

🔄 Compare: Reactive vs Proactive

Reactive (Panic)

"Restart everything! Everything will be fixed."

Risk: Problem temporary hide hota hai, solve nahi.

VS

Proactive (SRE)

"Check Vitals ➔ Read Logs ➔ Fix Root Cause."

Benefit: Permanent fix and data for post-mortem.

Jagu

"Fixing without evidence is like driving away darkness!"

⚠ COMMON MISCONCEPTIONS
  • Myth: Restart fix is always the best fix.
  • Reality: Restarts destroy evidence (logs in /tmp or RAM). Only restart if you know why.
  • Myth: Troubleshooting is only for 'Experts'.
  • Reality: Simple commands + a solid Runbook (checklist) can make anyone an expert.
▶ TRY IT YOURSELF
