💡 Mental Model

DevSecOps pipeline is like an international airport security checkpoint. Your code (passenger) must pass through multiple screening layers:

SAST (Code Scanner) → Like checking passport & visa before entering the terminal.
SCA (Dependency Scanner) → Like checking luggage for prohibited items (govulncheck/npm audit).
Container Scan → Like X-ray scanning your carry-on bag (Trivy was your Docker image).
Secret Scan → Like a metal detector checking for hidden weapons in your pockets (GitLeaks).
DAST (Runtime Scan) → Like a bomb-sniffing dog checking the plane before takeoff (OWASP ZAP).
CI Gate → If ANY check fails (CRITICAL/HIGH found) → Boarding denied. Image not pushed.
📈 Did You Know?
Shift Left

Catching a vulnerability in code (SAST) costs 10x less than fixing it in production. The earlier, the cheaper!

OWASP Top 10

DAST (OWASP ZAP) tests for the 10 most critical web app security risks including injection, XSS, and broken access control.

Trivy CVE DB

Trivy compares every Docker layer against 20,000+ known CVEs. CRITICAL findings block the build — MEDIUM/LOW get reported only.

⚙️ Security Scanning Types

1. SAST — Static Application Security Testing

Analyses source code without executing it. Runs early in the pipeline (Shift Left).

Tools: Bandit (Python), flake8/ESLint (JS/TS), go vet (Go), SonarQube (multi-language)
Catches: SQL injection patterns, hardcoded credentials, unsafe imports, code smells
When: On every push/PR — runs in parallel with other CI checks

2. SCA — Software Composition Analysis (Dependency Scan)

Scans third-party libraries and packages for known vulnerabilities (CVEs).

Tools: govulncheck (Go), npm audit (Node), Dependabot, Snyk
Catches: Libraries with known CVEs, outdated packages with security patches
Configuration: continue-on-error: true — reports vulnerabilities but doesn't fail by default
Output: Report uploaded as artifact with 5-day retention

3. Container Scanning — hadolint + Trivy

Two-stage Docker security check: first lint the Dockerfile, then scan the built image.

Stage 1 — hadolint: Lints Dockerfile for best practices (avoid root, optimize layers, proper labels)
Stage 2 — Trivy: Scans built image against CVE database for OS and library vulnerabilities
Matrix Strategy: Runs for both [backend, frontend] in parallel with fail-fast: false

4. Secret Scanning — GitLeaks

Detects accidentally committed secrets (API keys, tokens, passwords) using regex + entropy detection.

Tool: GitLeaks — scans full Git history (fetch-depth: 0)
Why full history? A secret may have been committed earlier and later removed — scanning only the latest commit misses old leaks
Detects: AWS keys, GitHub tokens, private SSH keys, JWT tokens, generic passwords

5. DAST — Dynamic Application Security Testing

Tests the running application by simulating real attacks. Runs last — after deployment.

Tool: OWASP ZAP Baseline Scan
What it checks: OWASP Top 10 categories (injection, XSS, CSRF, etc.)
Prerequisite: App must be live and healthy — includes a curl-based retry loop waiting for port 8080
Fail mode: failAction: false (team decision — can be set to true for strict enforcement)
⚠️ Severity Gating System

Every CVE has a severity. Pipeline decides which findings to block the build and which to report only.

CRITICAL

Block the build/deploy. Must be fixed immediately. CI fails with exit-code: 1.

HIGH

A patch is usually available. Should be fixed promptly. CI can also fail on these.

MEDIUM

Acceptable for now. Track but do not block the pipeline.

LOW

Can generally be ignored. Simply reported for awareness.

Production Pipeline Rule: CI is configured to fail on CRITICAL/HIGH findings (security "gate"). MEDIUM/LOW are simply reported via artifacts.

🏗️ DevSecOps Pipeline Architecture

A master workflow devsecops.yml orchestrates everything. Every CI job calls reusable workflow with uses: keyword.

Master Pipeline: devsecops.yml

# Goal: To Run End-to-End DevSecOps CI Pipeline
name: DevSecOps
on:
  push:
    branches: [master]

jobs:
  # === CI Stage (Parallel — All Security Checks) ===
  code-quality:
    uses: .github/workflows/code-quality.yml

  secret-scanning:
    uses: .github/workflows/secret-scanning.yml

  dependency-checks:
    uses: .github/workflows/dependency-scan.yml

  docker-checks:
    uses: .github/workflows/docker-scans.yml
    secrets: inherit    # Needs DockerHub auth

  sonar-qube:
    uses: .github/workflows/sonar-scan.yml
    secrets: inherit    # Needs SONAR_TOKEN

  code-tests:
    uses: .github/workflows/code-tests.yml

  # === Build Stage (Only if ALL CI checks pass) ===
  docker-push:
    needs: [code-quality, code-tests, sonar-qube,
            docker-checks, dependency-checks, secret-scanning]
    uses: .github/workflows/docker-push.yml
    secrets: inherit

  # === Deploy Stage (Only if image is pushed) ===
  deploy:
    needs: [docker-push]
    uses: .github/workflows/deploy.yml
    secrets: inherit

  # === Runtime Security (Only after deploy) ===
  dast-scan:
    needs: [deploy]
    uses: .github/workflows/dast.yml
    secrets: inherit

dast-scan (OWASP ZAP)

Note: This dependency chain is the real security "gate" of DevSecOps. If SAST, secret scanning, or SonarQube fails, the image will never be built or pushed.

Key Workflow Concepts

  • uses: — specifies which reusable workflow file to call (like a function call)
  • needs: [] — defines which jobs must succeed first (dependency chain)
  • secrets: inherit — passes the parent's secrets to the child workflow. Only jobs needing auth (Docker, SonarQube) use this.
  • on: push branches: [master] — defines the trigger condition
  • CI jobs run in parallel as a gate; CD jobs run sequentially afterward
  • Every child workflow uses on: workflow_call — they are only executed via devsecops.yml, not independently
📁 Workflow File Reference

code-quality.yml — SAST (Static Code Analysis)

name: Code Quality
on: workflow_call
jobs:
  sast:
    runs-on: ubuntu-latest
    steps:
      - name: Code Checkout
        uses: actions/checkout@v4
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: npm
          cache-dependency-path: frontend/package-lock.json
      - name: Install npm Packages
        run: npm install --legacy-peer-deps
        working-directory: frontend
      - name: Run Linter
        run: npm run lint
        working-directory: frontend
      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.23'
          cache-dependency-path: go.sum
      - name: Run Go Formatter
        run: go fmt ./...
        working-directory: backend
      - name: Run Go Vet
        run: go vet ./...
        working-directory: backend

code-tests.yml — Unit Tests

name: Code Tests
on: workflow_call
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version: '1.23', cache-dependency-path: go.sum }
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: npm, cache-dependency-path: frontend/package-lock.json }
      - run: npm install --legacy-peer-deps
        working-directory: frontend
      - run: npm run test
        working-directory: frontend
      - run: go test ./...
        working-directory: backend

dependency-scan.yml — SCA (Software Composition Analysis)

name: Dependency Scan
on: workflow_call
jobs:
  dependency-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version: '1.23', cache-dependency-path: go.sum }
      - name: Install Govulncheck
        run: go install golang.org/x/vuln/cmd/govulncheck@latest
      - name: Go Vulncheck
        continue-on-error: true
        run: govulncheck ./... > govulncheck-report.txt
        working-directory: backend
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: npm, cache-dependency-path: frontend/package-lock.json }
      - name: Run npm Audit
        run: npm audit
        working-directory: frontend
        continue-on-error: true
      - name: Upload Report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: dependency-scan-report
          path: backend/govulncheck-report.txt
          retention-days: 5

docker-scans.yml — Container Security (hadolint + Trivy)

name: Docker Scan
on: workflow_call
jobs:
  docker-file-lint-and-scan:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        folders: [backend, frontend]
    steps:
      - uses: actions/checkout@v4
      - name: ${{ matrix.folders }} Dockerfile Lint
        uses: hadolint/hadolint-action@v3.1.0
        with:
          dockerfile: ${{ matrix.folders }}/Dockerfile
      - name: Docker Setup Login
        uses: docker/login-action@v3
        with:
          username: ${{ vars.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - name: Docker Build ${{ matrix.folders }}
        run: docker build -t ${{ vars.DOCKERHUB_USERNAME }}/devboard-${{ matrix.folders }}:latest .
        working-directory: ${{ matrix.folders }}
      - name: Run Trivy Scanner
        uses: aquasecurity/trivy-action@0.30.0
        # Note: continue-on-error: true lets the job report findings without
        # failing the pipeline. The exit-code: 1 tells Trivy to return a non-zero
        # exit code when CRITICAL vulnerabilities are found, but continue-on-error
        # overrides this so the scan results are visible without blocking.
        # For strict enforcement, set continue-on-error: false.
        continue-on-error: true
        with:
          image-ref: ${{ vars.DOCKERHUB_USERNAME }}/devboard-${{ matrix.folders }}:latest
          format: table
          exit-code: 1
          ignore-unfixed: true
          vuln-type: os,library
          severity: CRITICAL

docker-push.yml — Build & Push (Final CI Step)

name: Docker Push
on: workflow_call
jobs:
  push:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        folders: [backend, frontend]
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          username: ${{ vars.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: ./${{ matrix.folders }}
          push: true
          tags: ${{ vars.DOCKERHUB_USERNAME }}/devboard-${{ matrix.folders }}:latest

secret-scanning.yml — GitLeaks

name: Secret Scanning
on: workflow_call
jobs:
  gitleaks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: GitLeaks Scan
        uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

dast.yml — OWASP ZAP Baseline Scan

name: DAST Scan
on: workflow_call
jobs:
  zap:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Wait for Service Health
        run: |
          for i in {1..30}; do
            curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/health && break
            sleep 10
          done
      - name: OWASP ZAP Scan
        uses: zaproxy/action-baseline@v0.14.0
        with:
          target: 'http://localhost:8080'
          failAction: false

deploy.yml — CD (Self-Hosted Runner)

name: Deploy
on: workflow_call
jobs:
  deploy:
    runs-on: self-hosted
    steps:
      - uses: actions/checkout@v4
      - name: Setup Environment
        run: cp env.example .env
      - uses: docker/login-action@v3
        with:
          username: ${{ vars.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - name: Pull and Restart
        run: docker compose pull && docker compose up -d
🔑 Secrets vs Vars — When to Use What
Secrets

Sensitive data — encrypted, never exposed in logs

  • DOCKERHUB_TOKEN
  • SONAR_TOKEN
  • GITHUB_TOKEN
  • Database passwords & API keys
VS
Vars

Non-sensitive config — plain text, visible in settings

  • DOCKERHUB_USERNAME
  • Environment names
  • Port numbers
  • Build configurations

✓ Quick Summary
  • Shift Left: Move security to the beginning of the pipeline, not the end
  • 5 scanning types: SAST (code), SCA (deps), Container (Docker), Secrets (GitLeaks), DAST (runtime)
  • Severity gates: CRITICAL/HIGH = Block build; MEDIUM/LOW = Report only
  • Master pipeline: devsecops.yml orchestrates 10+ child workflows via uses: and needs:
  • Dependency chain: All CI checks (parallel) → docker-push → deploy → dast-scan
  • Secrets vs Vars: Secrets = sensitive (encrypted); Vars = non-sensitive config
