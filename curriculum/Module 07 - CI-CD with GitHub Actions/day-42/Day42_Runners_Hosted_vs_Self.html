💡 Mental Model

GitHub-hosted runners are like rental cars—you get a clean, fresh car every time, use it, and return it. Self-hosted runners are like your own car—you have to wash it, service it, and pay for fuel, but you can customize it and park it inside your locked garage.

📈 Did You Know?
Zero Setup

GitHub-hosted runners require no server configuration or maintenance.

Full Isolation

GitHub-hosted VMs are immediately destroyed after the job finishes.

Persistent State

Self-hosted runners keep files on disk between jobs, speeding up cache but requiring cleanup.

📁 Core Concepts & Directories
  • GitHub-hosted runners run on virtual machines in Microsoft Azure cloud.
    • \n
  • Self-hosted runners require downloading a runner package and running the background listener.
    • \n
  • You route jobs to self-hosted runners using the `runs-on: self-hosted` label.
⚙️ Main Content

1. GitHub-Hosted Runners

Managed by GitHub, ephemeral, clean environments. Available for Linux, Windows, and macOS. CPU and memory configurations are pre-defined. Charged by the minute for private repositories (free for public repos).

2. Self-Hosted Runners

Configured on your own hardware or cloud instance. Persistent file storage enables faster builds (like locally cached tools) but carries security risks: if someone opens a malicious PR on a public repo, they can run arbitrary code inside your network. Never use self-hosted runners for public repositories!

3. Setup Concepts

To register a runner, go to repository Settings -> Actions -> Runners -> New self-hosted runner, and run the configuration script on the host server.

⌨️ Try It Yourself
# YAML snippet for routing to a custom self-hosted runner:
jobs:
  deploy:
    runs-on: [self-hosted, linux, internal-network]
    steps:
      - run: echo "Running on private internal infrastructure!"
📝 Day 42 Mini Quiz
1. Why is it highly recommended NOT to use self-hosted runners for public repositories?
A) It is slower than GitHub-hosted runners.\nB) Attackers can submit malicious pull requests that run code accessing your private network.\nC) GitHub charges extra for self-hosted runners.\nD) The runner agent only installs on Windows.
2. What happens to a GitHub-hosted runner VM after a job finishes execution?
A) It goes into sleep mode to save energy.\nB) It is shut down and immediately destroyed, wiping all state.\nC) It remains active for the next job of the same user.\nD) It copies all data to the developer's laptop.

Answer Key:

1: B (Forked pull requests can execute malicious code on your private server), 2: B (The runner VM is ephemeral and completely destroyed after one job)
