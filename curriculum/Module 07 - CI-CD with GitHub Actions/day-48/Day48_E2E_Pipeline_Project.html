⚙️ Main Content

1. Designing the E2E Pipeline

Our project will consist of three key phases:

  • Phase 1: Integration (Lint & Test): Run code analysis and verify code correctness on push or pull requests.
  • Phase 2: Registry Release: Build a Docker container and push it with the Git SHA tag to a registry.
  • Phase 3: Controlled Deploy: Deploy to Staging immediately. Trigger a pause gate for Production, resuming only when approved by a reviewer.

2. Job Environment Definition

deploy-prod:
  needs: [build-and-push]
  runs-on: ubuntu-latest
  environment:
    name: production
    url: https://my-app.com

📝 Day 48 Mini Quiz
1. Where in the GitHub repository settings do you configure manual approval rules for deployment jobs?
A) Branches settings\nB) Actions -> Runners settings\nC) Environments settings\nD) Secrets and variables settings
2. Why should testing and building be isolated from deployment jobs using 'needs' dependencies?
A) To ensure only verified code is packaged and deployed, preventing broken builds from pushing to servers.\nB) To make YAML look longer.\nC) Because runners do not support multiple jobs.\nD) To save electricity.

Answer Key:

1: C (Environments settings enable manual reviewer rules), 2: A (Ensures pipeline integrity and prevents broken deployments)
