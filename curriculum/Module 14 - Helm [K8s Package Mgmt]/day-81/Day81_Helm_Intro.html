📦 The YAML Sprawl Problem

One microservice needs at minimum:

  • Deployment (image, replicas, probes, resources)
  • Service (ports, selector)
  • ConfigMap (env, config)
  • Ingress (routing, TLS)
  • HPA (scaling policy)

× 50 services × 3 environments = 750+ YAML files. Helm packages one service's YAML into one chart, parameterized by values.yaml.

Without Helm                    With Helm
┌──────────────────┐            ┌──────────────────┐
│ deployment.yaml  │            │  mychart/        │
│ service.yaml     │            │  ├─ Chart.yaml   │
│ configmap.yaml   │            │  ├─ values.yaml  │
│ ingress.yaml     │  ONE APP   │  └─ templates/   │
│ hpa.yaml         │ ─────────→ │                  │
│ +30 more lines   │            │  helm install    │
│ per file, copied │            │  my-release      │
│ per environment  │            │  ./mychart       │
└──────────────────┘            └──────────────────┘
🏗️ Helm v3 Architecture

Helm v3 is client-only. There is no Tiller server component anymore — the client talks directly to the Kubernetes API:

┌──────────────┐   helm install    ┌─────────────────────┐
│ Helm Client  │ ────────────────→ │ Kubernetes API       │
│ (your CLI)   │                   │  → render chart      │
│              │                   │  → create resources  │
│ charts/      │                   │  → store release in  │
│ values/      │                   │    a Secret          │
└──────────────┘                   └─────────────────────┘
       │                                    │
       └────── talk to cluster ─────────────┘
              (kubeconfig / kubecontext)

Key Point: Release state is stored as a Kubernetes Secret in the release's namespace — no extra infrastructure to run.

📁 Chart Anatomy — What Lives Where
mychart/
├── Chart.yaml          # name, version, description, dependencies
├── values.yaml        # default config values (user overridable)
├── charts/            # subcharts (dependencies, e.g. postgres)
├── crds/             # Custom Resource Definitions
├── templates/
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── ingress.yaml
│   ├── _helpers.tpl    # reusable name/label helpers
│   └── NOTES.txt        # shown after install
└── .helmignore        # files excluded from packaging
🗂️ Repositories & Artifact Hub
# Add the Bitnami repository
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update

# Search your repos
helm search repo nginx

# Search ALL public charts on Artifact Hub
helm search hub kafka

# Pull a chart to inspect it
helm pull bitnami/nginx --untar

Jagu's Tip: Bitnami charts are battle-tested. Always check the chart's values.yaml before deploying!

🔄 Release Lifecycle
# Install (creates a release)
helm install my-nginx bitnami/nginx

# List releases
helm list
helm list -A          # all namespaces

# Upgrade with new values
helm upgrade my-nginx bitnami/nginx --set service.type=NodePort

# History & rollback
helm history my-nginx
helm rollback my-nginx 1

# Delete
helm uninstall my-nginx

Remember: helm install = first deploy; helm upgrade --install = deploy or update (idempotent).

⚖️ Compare: kubectl apply vs Helm

kubectl apply -f

  • One-off YAML files, copy-pasted per env.
  • No versioning, no rollback of "the app".
  • No parameterization without scripting.
  • Works, but doesn't scale.

helm install

  • One chart = full application definition.
  • Releases are versioned → helm rollback.
  • values.yaml = env-specific config.
  • Templates + packages + repos built in.
🌍 Real-World Example

Airbnb → the "multi-service release": Before Helm, Airbnb engineers updated dozens of Deployments by hand during deploys — one typo meant a broken rollout. After adopting Helm, each service ships as a chart with a versioned release. A bad deploy is now a 30-second helm rollback, and environment drift (dev vs prod configs) disappeared because each env uses its own values-*.yaml.

# The exact command pattern Airbnb-style teams run on every deploy
helm upgrade --install payments ./payments-chart \
  -f values-prod.yaml -n prod --atomic
🚫 Common Misconceptions
  • "Helm needs a server component." Not since v3 — it's client-only, using Kubernetes Secrets for state.
  • "Helm only deploys public charts." You write your own charts for YOUR apps — that's Day 82!
  • "Helm replaces kubectl." No — Helm renders templates and calls kubectl-style APIs. You still need kubectl for day-2 ops.
  • "Charts are just YAML copies." Charts are parameterized templates — one chart, many environments.

⚡ Quick Summary
  • Helm = the package manager for Kubernetes — one chart, one command.
  • Helm v3 is client-only; releases are stored as Kubernetes Secrets.
  • Chart = Chart.yaml + values.yaml + templates/ + helpers.
  • Repos (Bitnami) and Artifact Hub give you thousands of ready charts.
  • Lifecycle: install → upgrade → history → rollback → uninstall.
