🧬 Distributed Tracing

A trace is one request's journey. Each step is a span with a name, duration, and parent:

Trace: POST /checkout
├── span: api-gateway        (total 2100ms)
│   ├── span: auth-service   (150ms)
│   └── span: payment-svc    (1900ms)  ← BOTTLENECK!
│       └── span: db-query   (1750ms)  ← slow index?

Key insight: metrics say "server is fine", logs say "one line each". Only a trace connects the dots across services.

📡 OpenTelemetry & OTLP
  • OpenTelemetry = vendor-neutral standard for emitting telemetry.
  • One SDK per language instruments traces + metrics + logs together.
  • Data is exported via OTLP (OpenTelemetry Protocol) over gRPC/HTTP.
  • Optional Collector receives, processes, and routes telemetry anywhere.
# Export a span from the CLI (just to feel it)
otel-cli span --name "my first span" --kind client \
  --attributes "env=dev,team=platform"

# Typical pipeline
App (OTel SDK) --OTLP--> Collector --OTLP--> Tempo/Jaeger/Datadog

Jagu's Tip: Instrument once with OTel — switch backends later without touching code.

🚨 Prometheus Alert Rules
groups:
  - name: node-alerts
    rules:
      - alert: HighCPUUsage
        expr: 100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 80
        for: 5m                 # must hold 5 min → no flapping
        labels:
          severity: critical
        annotations:
          summary: "High CPU on {{ $labels.instance }}"
          runbook: "https://wiki.example.com/runbooks/cpu"

# Validate
promtool check rules rules.yml

Anatomy: expr (when to fire) + for (how long to sustain) + labels (who/severity) + annotations (what to say).

📮 Alertmanager Config
route:
  group_by: ['alertname']      # bundle related alerts
  group_wait: 30s              # wait before first notify
  receiver: 'webhook'

receivers:
  - name: 'webhook'
    webhook_configs:
      - url: 'http://localhost:5000/alert'
        send_resolved: true

# Run it
docker run -d --name alertmanager -p 9093:9093 \
  -v $PWD/alertmanager.yml:/etc/alertmanager/alertmanager.yml \
  prom/alertmanager

Also point Prometheus at it: add alerting: alertmanagers: - static_configs: - targets: ['localhost:9093'] to prometheus.yml.

⚖️ Compare: Alert on Symptoms vs Causes

Alert on Causes ❌

  • "nginx restarted" — so what? Users don't care.
  • High alert noise → engineers ignore alerts.
  • No link to user impact.

Alert on Symptoms ✅

  • "5xx error rate > 1% for 5m" — users are affected.
  • Fewer, meaningful pages.
  • Every alert has a runbook & severity.
  • Tie each symptom to an SLO / error budget — page when the burn rate threatens it.
🌍 Real-World Example

Uber: With millions of ride requests, a 100ms slowdown anywhere cascades. Uber uses OpenTelemetry-compatible tracing across 2,000+ microservices. When a dispatch latency spike happens, an alert fires before riders notice, and the on-call engineer opens the trace to see exactly which service (and even which database query) caused the delay — typically a 5-minute fix instead of a 3-hour outage.

# The alert that would page Uber's dispatch team
expr: histogram_quantile(0.99, rate(dispatch_latency_seconds_bucket[5m])) > 2
for: 10m
🚫 Common Misconceptions
  • "OTel is a tracing tool." It's a full telemetry standard — traces, metrics, and logs with one SDK.
  • "More alerts = safer system." False — alert fatigue causes real incidents to be ignored.
  • "Alertmanager = Prometheus." They're separate components; Prometheus evaluates, Alertmanager notifies.
  • "Tracing needs special infrastructure." The OTel collector + a trace backend (Tempo/Jaeger) run fine on one box.

⚡ Quick Summary
  • Traces = one request through many services; spans = each step.
  • OpenTelemetry = one SDK for metrics + logs + traces, exported via OTLP.
  • Alert rules: expr + for + labels + annotations.
  • Alertmanager groups, routes, and delivers alerts (webhook/email/Slack).
  • Alert on symptoms, keep for durations, and always link a runbook.
  • Silences stop noisy alerts during maintenance windows.
