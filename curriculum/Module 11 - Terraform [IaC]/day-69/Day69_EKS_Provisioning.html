💡 ANALOGY: Building an Airport Terminal

Think of an EKS cluster deployment like building a international airport:

1. Control Tower (Control Plane): Configured automatically by AWS to manage flight schedules (orchestrating pods).
2. Runways & hangars (Worker Nodes): Managed by node groups where planes (containers) actually land and load passengers.
3. Custom Modules: The master blueprint. Instead of laying down individual asphalt stones, you say "Place 3 runways here."

📌 Key Concepts: EKS Networking & Compute Modules

1. EKS Network Subnet Architecture

EKS clusters require public subnets (for external load balancers) and private subnets (where worker nodes host pod runtimes). Tags are mandatory for subnet discovery:

# Public Subnets Tag: kubernetes.io/role/elb = 1
# Private Subnets Tag: kubernetes.io/role/internal-elb = 1

2. EKS Control Plane and Compute Configuration

module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 19.0"

  cluster_name    = "my-eks-cluster"
  cluster_version = "1.27"

  vpc_id     = module.vpc.vpc_id
  subnet_ids = module.vpc.private_subnets

  eks_managed_node_groups = {
    general = {
      min_size     = 1
      max_size     = 3
      desired_size = 2

      instance_types = ["t3.medium"]
    }
  }
}

3. Authenticating client with kubectl

Once deployment completes, update local kubeconfig credentials:

aws eks update-kubeconfig --region us-east-1 --name my-eks-cluster
🔄 Compare: Managed Nodes vs Self-Managed

Self-Managed Nodes

You manually provision EC2 instances, install kubelet, join cluster, and manage OS patches. Painful.

VS

Managed Node Groups

AWS handles scaling, OS updates, node draining, and cluster joining automatically. Recommended.

📖 REAL-WORLD EXAMPLE: EKS Cluster Validation

Scenario: You successfully deployed the EKS infrastructure, but want to verify the cluster nodes are healthy.

Solution: Update your kubeconfig and query nodes:

# Update config
$ aws eks update-kubeconfig --name my-eks-cluster

# Check nodes status
$ kubectl get nodes

⚠ COMMON MISCONCEPTIONS
  • Myth: t2.micro instance type is suitable for running EKS node groups.
  • Reality: No! EKS node groups require running Kubernetes agent system containers (kubelet, kube-proxy, aws-node) which consume memory. t2.micro (1GB RAM) will run out of memory before your pods run. Use at least t3.medium (4GB RAM).
