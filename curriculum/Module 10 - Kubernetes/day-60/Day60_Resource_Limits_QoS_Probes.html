1. Learning Objectives

Container memory and CPU limit karna, quality of service setup karna, aur self-healing configurations define karna.

  • Requests & Limits: Allocation of CPU/Memory resources.
  • QoS Classes: Guaranteed, Burstable, and BestEffort eviction priorities.
  • Probes: Liveness, Readiness, and Startup health checks.
2. Analogy & Mental Model

Think of resources and health probes like restaurant operations:

  • Resource Requests (Seat reservation): Table size reserved for you (e.g. table for 2). You are guaranteed to get it.
  • Resource Limits (Max food order): The maximum amount you can order. If you order more, the manager stops you (OOMKill).
  • Startup Probe (Checking if chef arrived): Checks if the kitchen is booted.
  • Readiness Probe (Checking if food is cooked): Don't seat guests at the table until the food is ready to serve.
  • Liveness Probe (Checking if customer is choking): If the customer stops breathing, the waiter intervenes (restarts container).

4. Resource & Probes Specifications

Pod manifest: resources-probes-pod.yaml

apiVersion: v1
kind: Pod
metadata:
  name: robust-app
spec:
  containers:
  - name: app
    image: nginx:alpine
    resources:
      requests:
        memory: "64Mi"
        cpu: "250m"
      limits:
        memory: "128Mi"
        cpu: "500m"
    readinessProbe:
      httpGet:
        path: /index.html
        port: 80
      initialDelaySeconds: 5
      periodSeconds: 10
    livenessProbe:
      httpGet:
        path: /index.html
        port: 80
      initialDelaySeconds: 15
      periodSeconds: 20
5. Key Concepts

Resource Requests vs Limits

  • Requests: Used by Scheduler to find a node with enough space. Guaranteed computation resources.
  • Limits: Enforced by host kernel. If container uses more CPU, it is throttled. If it uses more Memory, it is OOMKilled.

QoS Classes

  • Guaranteed: Requests == Limits for all containers. Highest priority, deleted last.
  • Burstable: Requests < Limits. Medium priority.
  • BestEffort: No requests or limits specified. Lowest priority, deleted first.
6. Compare: Liveness vs Readiness Probes
Liveness Probe
  • Checks if container is alive
  • Restarts the container on failure
  • Protects against deadlocks, loops
  • Can cause restart loops if configured badly
VS
Readiness Probe
  • Checks if application is ready to accept traffic
  • Temporarily removes pod from Service endpoints
  • Protects users from receiving HTTP 502/503 errors
  • Never restarts the container
7. Real-World Troubleshooting Example

Incident: A pod keeps restarting every 30 seconds with OOMKilled status.

Resolution: The DevOps engineer runs `kubectl describe pod` and inspects termination reasons. Finding Exit Code 137 (OOMKilled), the engineer raises the memory limit in the manifest from 128Mi to 256Mi and updates the deployment. The app stabilized immediately.

8. Common Misconceptions
  • ❌ Myth: A failed readiness probe restarts the pod.
  • ✔️ Reality: It only stops traffic routing to it. Only liveness probe failures restart containers.
  • ❌ Myth: CPU limits cause OOMKilled events.
  • ✔️ Reality: High CPU limit hits only cause CPU throttling (app gets slower). Memory limit hits cause OOMKilled.
9. Try It Yourself

Check QoS class and resource stats via CLI:

# Apply pod
kubectl apply -f resources-probes-pod.yaml

# View pod details including QoS Class
kubectl get pod robust-app -o jsonpath='{.status.qosClass}'

# Check current node resource consumption
kubectl top nodes
10. Quick Summary
  • Requests guide scheduling; limits enforce maximum usage caps.
  • Readiness stops traffic; liveness restarts broken containers.
  • Always configure requests/limits to avoid BestEffort eviction.
