Kubernetes Architecture & Cluster Setup

Day 53: Brain vs Muscle & Setting up Kind ☸️

Section

1. Learning Objectives

Understand the basic architecture and components of Kubernetes, and setup Kind (Kubernetes in Docker) in the local environment.

  • Control Plane: API Server, etcd, Scheduler, Controller Manager.
  • Worker Nodes: Kubelet, Kube-Proxy, Container Runtime (containerd).
  • Cluster Setup: Kind CLI installation aur multinode cluster configuration.
2. Analogy & Mental Model

Think of a Kubernetes Cluster as a large shipping port:

  • Yard Office (Control Plane): The controllers, planners, and database tracking every box.
  • Cranes and Trucks (Worker Nodes): The physical resources doing the lifting and running.
  • Cargo Box (Pod): The smallest unit of shipping containing our application container.

4. Key Directories & Paths
  • 📂 /etc/kubernetes/manifests/ - Path on control-plane where static Pod configurations are placed (etcd, apiserver, scheduler, controller-manager).
  • 📂 /var/lib/kubelet/ - Directory holding kubelet state, volume mounts, and pod logs.
  • 📂 ~/.kube/config - Kubeconfig credential file for kubectl client.
5. Key Concepts

Control Plane (The Brain)

  • kube-apiserver: Rest API endpoint of the cluster. Everything connects here.
  • etcd: Highly available key-value store. The cluster's source of truth database.
  • kube-scheduler: Assigns newly created Pods to nodes based on affinity and resource requirements.
  • kube-controller-manager: Manages controllers like replicaset, deployments, and node health.

Worker Nodes (The Muscle)

  • kubelet: Node agent that pulls images and keeps containers running.
  • kube-proxy: Maintains network rules on hosts for Service communication.
  • container runtime (containerd): The engine executing the container processes.
6. Compare: Control Plane vs Worker Node
Control Plane
  • Decides cluster scheduling
  • Monitors and reconciles state
  • Tainted by default (no user apps)
  • Writes directly to etcd
VS
Worker Node
  • Runs user application Pods
  • Executes container lifecycles
  • Reports status to API server
  • Uses kube-proxy for routing
7. Real-World Troubleshooting Example

Incident: A worker node crashes physically due to RAM overload.

Resolution: The kube-controller-manager detects heartbeat loss. It marks the node as NotReady. The scheduler immediately creates replacement Pods on a remaining healthy node. Traffic is shifted to new nodes automatically, resulting in zero downtime for the users.

8. Common Misconceptions
  • ❌ Myth: Kubernetes runs containers directly.
  • ✔️ Reality: K8s uses standard container runtimes like containerd via CRI (Container Runtime Interface).
  • ❌ Myth: Local Kubernetes requires heavy VM resources.
  • ✔️ Reality: Tools like Kind run Kubernetes nodes as lightweight Docker containers on your laptop.
9. Try It Yourself

Install Kind and spin up a 3-node cluster. Create kind-config.yaml:

apiVersion: kind.x-k8s.io/v1alpha4
kind: Cluster
nodes:
- role: control-plane
- role: worker
- role: worker

Run CLI commands:

# Create cluster
kind create cluster --config kind-config.yaml --name devops-k8s

# Check status
kubectl cluster-info
kubectl get nodes
10. Quick Summary
  • Control Plane acts as the controller, etcd is the cluster state DB.
  • Worker Nodes execute workloads, managed by kubelet.
  • Kind is perfect for running Kubernetes in Docker containers for dev/test.
