1. Learning Objectives

Kubernetes will understand networking, configure internal routing, and seek dynamic routing using modern Gateway API.

  • Service Types: ClusterIP, NodePort, LoadBalancer.
  • DNS resolution: CoreDNS functionality and service discovery.
  • Gateway API: Gateway and HTTPRoute controllers replacing legacy Ingress.
2. Analogy & Mental Model

Think of Services as Support Hotlines:

  • Service (Main Hotline number): 1-800-WEB-HELP. It never changes.
  • Pods (Operators): The agents answering calls. They might shift, go offline, or get replaced, but callers only dial the main hotline number.
  • Gateway API (Receptionist desk): Routes callers to the sales or billing hotline based on what they ask for (e.g. `site.com/sales` vs `site.com/billing`).

4. Service and Gateway API Specs

Here is a basic Service manifest: service.yaml

apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 80

Here is a simple Gateway API HTTPRoute manifest: httproute.yaml

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: web-routes
spec:
  parentRefs:
  - name: my-gateway
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: web-service
      port: 80
5. Key Concepts

Service Types

  • ClusterIP (Default): Exposes the service on a cluster-internal IP. Accessible only inside cluster.
  • NodePort: Exposes the service on each static Port on every Node's IP.
  • LoadBalancer: Provisions an external cloud load balancer pointing to NodePorts.

Gateway API vs Ingress

Ingress is a single monolithic resource that combines routing configurations and load balancer details. Gateway API splits these concerns into separate resources (GatewayClass, Gateway, HTTPRoute), offering clean role separation between NetOps, Admin, and Developers.

6. Compare: Ingress vs Gateway API
Legacy Ingress
  • Monolithic YAML definition
  • Provider-specific annotations
  • Hard to delegate path access
  • Now frozen by Kubernetes community
VS
Gateway API
  • Role-oriented configuration
  • Standardized HTTPRoute specs
  • Extensible filters and headers
  • Recommended for all new deployments
7. Real-World Troubleshooting Example

Incident: Application Pods cannot resolve other Service endpoints by name.

Debugging Process:

# Check CoreDNS Pods in kube-system namespace
kubectl get pods -n kube-system -l k8s-app=kube-dns

# Run temporary container to test lookup
kubectl run dns-test --rm -it --image=busybox -- nslookup web-service

Often, this is due to incorrect Label Selectors on the Service or CNI network plugin issues.

8. Common Misconceptions
  • ❌ Myth: ClusterIP services are accessible from local browser directly.
  • ✔️ Reality: ClusterIP is strictly internal. To test locally, you must port-forward, or use NodePort/LoadBalancer.
  • ❌ Myth: Services load balance packets randomly on software level.
  • ✔️ Reality: Services use kube-proxy to configure OS-level iptables or IPVS rules for packet routing.
9. Try It Yourself

Create a Service, expose your web app, and verify endpoints:

# Create deployment & service
kubectl apply -f service.yaml

# List active endpoints linked to selector
kubectl get endpoints web-service

# Install Gateway API CRDs (standard channel)
kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.1.0/standard-install.yaml
10. Quick Summary
  • Services provide stable networking abstractions for Pods.
  • CoreDNS maps service names to IPs.
  • Gateway API is the modern successor to Ingress for L7 traffic routing.
