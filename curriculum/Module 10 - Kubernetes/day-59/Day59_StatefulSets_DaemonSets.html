StatefulSets & DaemonSets

Day 59: Sticky Identities & Per-Node Agents ☸️

Naked
"Jagu, standard deployments to databases do not seem safe. If Pod restarts, the name and disk may be mixed up like generic pods. What is the solution?"
"Golu, for databases and stateful services we use StatefulSets. Every Pod gets stable name (e.g. database-0, database-1) and separate volume index. And to run background worker on every server node we use DaemonSets!"
Section

1. Learning Objectives

Specialized workloads identify karna, database clustering network setup karna, aur per-node logging configure karna.

  • StatefulSets: Unique network identities and Headless service configuration.
  • DaemonSets: Continuous per-node processes (logging, monitoring agents).
  • Jobs & CronJobs: Run-to-completion and scheduled workloads.
2. Analogy & Mental Model

Think of K8s workload controllers like housing setups:

  • Deployments (Hotel Guests): Pods are identical, transient, and replaceable. Nobody cares which room they get.
  • StatefulSets (Home Owners): Pods have exact, dedicated addresses (e.g., House 0, House 1). They keep their specific garden (disk volume) even if they go on vacation.
  • DaemonSets (Security Guards): Exactly one guard stands in front of every building (node) to secure it. If a new building is built, a new guard is sent automatically.

4. Key YAML Structures

Headless Service (clusterIP: None): headless.yaml

apiVersion: v1
kind: Service
metadata:
  name: mongo-service
spec:
  clusterIP: None
  selector:
    app: mongodb
  ports:
  - port: 27017

StatefulSet: statefulset.yaml

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mongo-db
spec:
  serviceName: mongo-service
  replicas: 3
  selector:
    matchLabels:
      app: mongodb
  template:
    metadata:
      labels:
        app: mongodb
    spec:
      containers:
      - name: mongo
        image: mongo:latest
        ports:
        - containerPort: 27017
5. Compare: Deployments vs. StatefulSets
Deployments
  • Random, hash-based Pod names
  • Share volumes or mount generic ones
  • Pods scale in parallel
  • Ideal for stateless web APIs
VS
StatefulSets
  • Sticky, ordinal Pod names (db-0, db-1)
  • Dedicated volume per Pod index
  • Ordered scale up and down
  • Ideal for databases (MySQL, MongoDB)
6. Real-World Troubleshooting Example

Incident: A database node crashes, and the replacing pod cannot bind to the database data directory.

Resolution: Because it was deployed via a StatefulSet, K8s mounts the exact same PVC (e.g. datadir-mongo-db-0) to the recreated pod, keeping database journals intact and avoiding split-brain data corruption.

7. Jobs and CronJobs (Batch Workloads)
  • Jobs: Spin up a container, run a batch processing script, and exit on success (e.g. running DB migrations).
  • CronJobs: Scheduled tasks running Jobs at intervals (e.g. backing up database logs at midnight daily).
8. Common Misconceptions
  • ❌ Myth: DaemonSets require manually specifying node names in YAML.
  • ✔️ Reality: The DaemonSet controller automatically schedules exactly one Pod to run on every node in the cluster.
  • ❌ Myth: CronJobs run continuously.
  • ✔️ Reality: CronJobs are only active at the trigger time. They create a Job, run it, and terminate.
9. Try It Yourself

Check active workloads using commands:

# Get stateful sets status
kubectl get statefulset

# Get active daemonsets
kubectl get daemonset -A

# Check jobs status
kubectl get jobs
10. Quick Summary
  • StatefulSets manage database clusters with sticky names and dedicated storage.
  • DaemonSets deploy infrastructure agents to all nodes.
  • Jobs execute batch tasks; CronJobs run them on schedules.
