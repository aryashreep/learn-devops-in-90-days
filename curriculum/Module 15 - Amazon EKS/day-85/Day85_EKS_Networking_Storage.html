🌐 Pod Networking — the VPC CNI

EKS uses the AWS VPC CNI: every pod gets an IP straight from your VPC subnet. No overlay, no double-NAT — pod-to-pod traffic uses the VPC's routing and security groups natively.

Node (t3.medium, 10.0.1.12)
├── eth0  → 10.0.1.12      (node's ENI)
├── eth1  → 10.0.1.20      (pod A)
│            pod: ai-bankapp-abc12
└── eth2  → 10.0.1.21      (pod B)
             pod: ai-bank-redis-xyz98

Pods talk to each other using plain VPC IPs — same routing,
same security groups, sub-ms latency. No overlay tunnels!
  • Fast: traffic stays on the VPC network.
  • Secure: security groups can target pods directly (Security Groups for Pods).
  • Watch out: each node needs enough ENI/IP quota for its pods.

🚦 Ingress + AWS Load Balancer Controller

The AWS Load Balancer Controller turns an Ingress into a real ALB (Layer 7 — path & host routing, TLS, sticky sessions):

# 1. Give the controller its IAM role first (IRSA from Day 84)
curl -o iam_policy.json https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/main/docs/install/iam_policy.json
aws iam create-policy --policy-name AWSLoadBalancerControllerIAMPolicy \
  --policy-document file://iam_policy.json

eksctl create iamserviceaccount \
  --cluster ai-bank-cluster --namespace kube-system \
  --name aws-load-balancer-controller \
  --attach-policy-arn arn:aws:iam::<ACCOUNT>:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve

# 2. Install the controller with that service account
helm repo add eks https://aws.github.io/eks-charts
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=ai-bank-cluster \
  --set serviceAccount.name=aws-load-balancer-controller

# 2. Create the Ingress
kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ai-bankapp
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP": 80}]'
spec:
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: ai-bankapp
                port: { number: 80 }
EOF

# 3. Find the ALB DNS
kubectl get ingress ai-bankapp

Rule of thumb: Service type=LoadBalancer → NLB (L4). Ingress + ALB controller → ALB (L7).

💾 Storage: EBS vs EFS

EBS (block)

  • Attached to ONE node (single-AZ).
  • Fast, low latency — perfect for databases (mongo, postgres).
  • Use the EBS CSI driver (gp3 default).
  • PV bound to a node; reattach after failover.

EFS (shared file)

  • Mountable from MANY pods/nodes across AZs.
  • NFS-style — perfect for shared configs, media, uploads.
  • Use the EFS CSI driver.
  • Slower per-I/O, but elastic & multi-AZ.

Jagu's Rule: Database → EBS. Shared files → EFS. Both through PVCs!

🧱 PVC Example (EBS)
# pvc.yaml — request storage by SIZE, not by hardware
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: ai-bank-mongo
spec:
  accessModes: [ "ReadWriteOnce" ]
  storageClassName: gp2          # from the EBS CSI driver
  resources:
    requests:
      storage: 10Gi
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: ai-bank-mongo }
spec:
  selector: { matchLabels: { app: ai-bank-mongo } }
  template:
    metadata: { labels: { app: ai-bank-mongo } }
    spec:
      containers:
        - name: mongo
          image: mongo:7
          volumeMounts: [ { name: data, mountPath: /data/db } ]
      volumes:
        - name: data
          persistentVolumeClaim: { claimName: ai-bank-mongo }
kubectl apply -f pvc.yaml
kubectl get pvc           # Bound
kubectl get pv            # AWS created the EBS volume for you!
🌍 Real-World Example

E-commerce → the Black-Friday scale story: A retailer's EKS platform routed ALL traffic through a single nginx Ingress — on peak day it became the bottleneck. They moved to the AWS Load Balancer Controller: the ALB handled TLS termination, path routing (/api → backend, / → web), and scaled its targets automatically. Databases moved to EBS-backed StatefulSets with the CSI driver, and shared product images moved to EFS. The platform absorbed 10× traffic with zero ingress changes.

🚫 Common Misconceptions
  • "Pods use NAT to talk to each other." No — the VPC CNI gives real VPC IPs; no overlay needed.
  • "LoadBalancer = ALB." The default Service LoadBalancer is an NLB (L4). ALB comes from Ingress + the ALB controller.
  • "EBS volumes follow pods anywhere." EBS is single-AZ — a pod must land on a node in that AZ to attach it.
  • "Storage is free in Kubernetes." EBS/EFS are real AWS services — they cost money and need cleanup.
🛠️ Try It Yourself
# On your Day 84 cluster (or any EKS cluster):
kubectl create deploy nginx --image nginx

# 1. ClusterIP → NodePort → LoadBalancer
kubectl expose deploy nginx --port 80
kubectl get svc nginx
kubectl delete svc nginx
kubectl expose deploy nginx --port 80 --type=NodePort
kubectl expose deploy nginx --port 80 --type=LoadBalancer   # NLB
kubectl get svc nginx -w

# 2. EBS storage via PVC
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: test-ebs }
spec:
  accessModes: [ "ReadWriteOnce" ]
  resources: { requests: { storage: 1Gi } }
EOF
kubectl get pvc test-ebs   # Bound → EBS volume created

# 3. (Bonus) install the ALB controller + an Ingress
kubectl get ingress -A

⚡ Quick Summary
  • VPC CNI = real VPC IPs for every pod — fast, secure, no overlay.
  • Services: ClusterIP (internal), NodePort (nodeIP:port), LoadBalancer (NLB, L4).
  • ALB Ingress = Layer 7 routing via the AWS Load Balancer Controller.
  • EBS = block storage, single-AZ, for databases (gp3 by default).
  • EFS = shared file storage, multi-AZ, for shared volumes.
  • Request storage with PVCs — the cloud provider creates the real volume.
